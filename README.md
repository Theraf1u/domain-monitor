# 🖥 Domain Monitor

Мультинодовая система мониторинга доменов для VPN-инфраструктуры. Ставится
на любое количество VPN-нод (агенты) и собирает данные в единый центр
управления (сервер) — управление полностью через Telegram, без браузера.

Изначально создавался как инструмент для построения whitelist-роутинга:
чтобы определить, с какими доменами общаются российские приложения
(банки, госуслуги, маркетплейсы), и пропускать их трафик напрямую, минуя
VPN — а весь остальной трафик заворачивать в туннель как обычно.

```
                     ┌─ Agent Germany
                     │
Клиенты → VPN ───────┼─ Agent Netherlands
                     │
                     ├─ Agent Finland
                     │
                     └─ Agent Kazakhstan
                              │
                              ▼
                    Domain Monitor Server
                              │
                          Telegram
```

## Что внутри

| Компонент | Что делает |
|---|---|
| [`server/`](server) | Центральный backend: REST API (для агентов) + Telegram-бот (для тебя) |
| [`agent/`](agent) | Лёгкий агент на самой VPN-ноде: захватывает домены и шлёт на сервер |

Ставятся раздельно — сервер один раз, агенты на каждую ноду по мере
надобности. **Браузер нигде не участвует** — всё управление (ноды, домены,
фильтры, уведомления) только через Telegram-бота.

## Возможности

**Обнаружение доменов**
- Пассивный захват через `tshark`, без MITM и расшифровки трафика —
  только чтение SNI из TLS-хендшейка и имён из DNS-запросов
- Два независимых источника: TLS SNI и DNS-запросы (каждый — отдельный
  процесс tshark, можно включать/выключать по отдельности)
- Не хранит содержимое пакетов — только домен, время, нода, источник

> ⚠️ **Важно, если у ноды в Remnawave уже выбран не дефолтный шаблон
> роутинга (xray config с split-роутингом)**: Agent видит только тот
> трафик, что реально проходит через сниффер на интерфейсе ноды. Если в
> шаблоне уже настроен прямой роутинг (bypass VPN) для части доменов —
> например, весь `.ru` / `.su` / `.рф` уходит в обход туннеля напрямую —
> то именно эти домены Agent не увидит и не соберёт, поскольку они не
> идут через тот же путь, что и остальной проксируемый трафик.
>
> Если цель — собрать **полный** список доменов (в том числе для
> построения будущего whitelist-роутинга), на время сбора статистики
> выставь на ноде **стандартный дефолтный шаблон**, где весь трафик без
> исключений идёт через VPN. Так Agent увидит вообще все домены, включая
> те, что потом попадут в whitelist на прямой роутинг. Уже настроенный
> split-роутинг можно вернуть обратно после того, как список доменов
> собран.

**Мультинода**
- Любое количество агентов, у каждого свой отзываемый токен
- Токены: генерация, ревок, регенерация — без паролей и SSH между
  компонентами, только `Authorization: Bearer` по HTTPS
- Имя ноды по умолчанию — её публичный IP (не hostname): при установке
  через `install.sh` (пункт «Оба») нода в списке сразу узнаваема, а не
  подписана случайным именем облачного провайдера
- Heartbeat с версией агента, IP, hostname — статус online/offline виден
  в реальном времени
- Локальный буфер на агенте (SQLite) переживает обрыв связи с сервером:
  события копятся и отправляются батчами с retry/backoff, при
  затянувшемся простое сервера — сначала теряются самые старые записи, а
  не всё подряд

**Telegram-бот — единственная панель управления**
- Управление только инлайн-кнопками, никаких команд кроме `/start`,
  кнопки окрашены (Bot API 9.4 `style`) — красный/зелёный/синий отражают
  реальный смысл действия, а не просто "красиво"
- Отвечает только заданному `ADMIN_ID`, все остальные молча игнорируются
- Карточки нод (статус, heartbeat, статистика, вкл/выкл мониторинга и
  уведомлений), создание/ревок/удаление ноды
- **Домены**: последние / топ по хитам, экспорт в `.txt` за выбранный
  период (сегодня / вчера / 24ч / 7д / 30д / всё время / свой диапазон
  дат), полный сброс собранных доменов и истории событий (с
  подтверждением, ноды/токены/фильтры не трогает)
- **Статистика**: те же периоды, плюс топ-3 активных ноды и скорость
  событий/час за период — не только суммарные цифры "за всё время"
- Группировка уведомлений о новых доменах: Instant / батч 5 / 15 / 30 /
  60 сек или свой интервал в секундах
- Управление Ignore / Allow / Watch листами (exact / suffix / wildcard)
  прямо из чата, с подтверждением перед удалением правила, пагинацией
  длинных списков и проверкой домена против текущих правил "что будет,
  если..."
- **Настройки** реально работают и применяются без перезапуска: срок
  хранения детальной истории событий, таймаут "нода = offline", вкл/выкл
  уведомлений о попаданиях в Watch-лист
- Автоматический перезапуск polling при обрыве соединения с Telegram
- Прямо в главном меню — два независимых глобальных выключателя для всей
  флотилии агентов сразу, без захода в карточку каждой ноды:
  **⏸ Остановить мониторинг** (агенты перестают захватывать трафик —
  tshark на нодах не запускается) и **⏸ Остановить отправку доменов**
  (агенты продолжают захват, но перестают слать события на сервер —
  копятся в локальном буфере до возобновления). Действуют сразу при
  следующем heartbeat, без перезапуска агента

**Фильтрация**
- **Ignore** — не уведомлять, домен помечается подавленным
- **Allow** — доверенный домен, тоже не уведомляет, но учитывается отдельно
- **Watch** — всегда мгновенное 🚨-уведомление, даже если совпадает с
  ignore/allow

**Эксплуатация**
- Установка одной командой с интерактивным мастером (проверяет свободный
  порт и доступность Telegram ещё на этапе установки)
- CLI: `status`, `logs`, `restart`, `update`, `doctor`, `backup`,
  `restore`, `uninstall`
- `doctor` — диагностика (Docker, конфиг, здоровье контейнера, доступность
  Telegram API, целостность БД, место на диске) с понятными рекомендациями
- Prometheus `/metrics` на сервере (для внешнего мониторинга, не для браузера)
- Полное удаление одной командой (включая опциональную очистку данных)

## Быстрый старт

Один установщик, который сам спросит что ставить:

```bash
curl -fsSL https://raw.githubusercontent.com/Theraf1u/domain-monitor/main/install.sh | sudo bash
```

(или `git clone https://github.com/Theraf1u/domain-monitor.git && cd domain-monitor && sudo bash install.sh`)

```
== Domain Monitor ==

1) Оба          - сервер (бот) и агент вместе, на этой же машине
2) Agent        - только сниффер трафика (ставится на каждую VPN-ноду)
3) Server       - только сервер + Telegram-бот (центральная точка управления)
4) Статус               - что установлено и работает
5) Диагностика          - проверить установленные компоненты
6) Управление скриптом  - переустановка, обновление
7) Выход
```

- **1) Оба** — самый частый сценарий: ставит сервер, дожидается его
  готовности, сам создаёт ноду через API (без похода в Telegram за
  токеном) и сразу настраивает и запускает агента с этим токеном. Удобно,
  если сервер и одна из VPN-нод — один и тот же сервак.
- **2) Agent** — если сервер уже стоит где-то ещё, а эта машина будет
  просто ещё одной VPN-нодой. Спросит URL сервера, токен ноды (получи его
  через бота: **📡 Ноды → ➕ Добавить**), имя и сетевой интерфейс.
- **3) Server** — только центральный сервер + бот. Спросит admin-ключ
  (можно сгенерировать автоматически), адрес сервера, свободный порт
  (по умолчанию `8280`, если занят — автоматически берётся следующий
  свободный), **Telegram BOT_TOKEN и твой ADMIN_ID** (обязательны — это
  единственный способ управления), и, если Telegram заблокирован на этом
  хосте — прокси (формат `socks5://host:port` или `http://host:port`,
  проверяется на вводе).
- **6) Управление скриптом** — отдельное подменю:
  - **Переустановить** — полный снос (контейнеры/образы/данные/`.env`) и
    сразу мастер установки заново, одним действием.
  - **Удалить** — то же самое, что было раньше пунктом «Удалить всё»:
    сносит вообще всё, включая CLI-команды и саму папку проекта.
  - **Обновить** — `git pull` + пересборка тех компонентов, что реально
    установлены на этой машине.
  - **Автообновление** — включает/выключает cron-задачу, которая сама
    делает `git pull` + пересборку по расписанию (ежедневно, раз в
    неделю или своё cron-выражение); лог — `auto-update.log` в папке
    проекта.

После установки открой бота в Telegram и нажми `/start`.

## Системные требования

Замерено на реальных продакшен VPN-нодах под живым трафиком (не синтетика).

**Agent** (сниффер трафика — самый ресурсоёмкий компонент, нагрузка растёт
вместе с количеством одновременных TCP-соединений, а не с объёмом трафика):

| | Минимум | Рекомендуется |
|---|---|---|
| CPU | 2 ядра | 4+ ядра |
| RAM | 1 ГБ | 2+ ГБ |
| Одновременных пользователей ноды | до ~50 | 200+ (проверено на 250) |

На ноде послабее (1-2 ядра, ~2 ГБ RAM) под нагрузкой в 150+ активных
пользователей агент не справлялся и приводил к падению производительности
всей ноды — не ставь на такие машины без явного запаса.

На 8-ядерной ноде с 250 одновременными пользователями агент в
установившемся режиме потребляет ориентировочно 150-300 МБ RAM и
40-66% от одного ядра CPU, с периодическим (раз в 10 минут) кратким
скачком при плановом перезапуске процесса захвата — это штатное поведение,
а не утечка (см. ниже).

По умолчанию заданы жёсткие лимиты контейнера `mem_limit: 1g` и `cpus: 2.0`
(правятся через `AGENT_MEM_LIMIT` / `AGENT_CPU_LIMIT` в `.env`) — это
страховка от неожиданного всплеска потребления, а не ожидаемый рабочий
режим: при столкновении с лимитом Docker перезапустит только контейнер
агента, не затрагивая остальные сервисы на ноде.

**Server** (API + Telegram-бот, ставится один раз в одном месте):

| | Минимум | Рекомендуется |
|---|---|---|
| CPU | 1 ядро | 2 ядра |
| RAM | 512 МБ | 1 ГБ |
| Диск | 500 МБ свободно | 2+ ГБ (зависит от числа нод/доменов) |

Нагрузка на сервер не зависит от трафика VPN-пользователей напрямую —
только от количества нод и частоты новых уникальных доменов.

## Архитектура

- **Agent → Server**: только HTTPS, `Authorization: Bearer <NODE_TOKEN>`.
  Ни SSH, ни паролей между компонентами
- **Хранилище**: SQLite поверх ручного слоя без ORM — схема маленькая,
  запросы простые, при необходимости миграция на Postgres требует
  изменений только в одном файле (`database.py`)
- **Только Telegram, без веб-интерфейса**: меньше поверхность атаки (нет
  сессий, нет CSRF, нет браузера), меньше двигающихся частей — один
  оператор, один канал управления
- **Host-сеть у сервера**: чтобы бот мог достучаться до локального прокси
  (например, VPN-клиента вроде Mihomo) на хосте — обычная bridge-сеть
  Docker часто не может маршрутизировать трафик в такой интерфейс

## Безопасность и приватность

- Содержимое трафика никогда не сохраняется — только домен/время/нода/источник
- Токен ноды и Telegram bot token автоматически вымарываются из логов
- Отозванный токен агента сразу возвращает 403 на любые попытки отправки
