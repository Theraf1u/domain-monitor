# Резервное копирование и восстановление

Два независимых механизма: **Backup Manager 2.0** (автоматический,
управляется из бота, живёт внутри контейнера, пишет в `data/backups/`)
и **CLI-скрипты** (`backup`/`restore`, ручные, работают с хостовой
`./backups/`, не требуют бота). У обоих одна и та же цель — снимок,
из которого можно восстановиться, но разные форматы и расположение,
см. таблицу ниже.

| | Backup Manager 2.0 (бот) | CLI (`backup`/`restore`) |
|---|---|---|
| Где хранится | `data/backups/` (в контейнере, том `./data`) | `./backups/` (только на хосте) |
| Типы | `db` (только БД) / `full` (+ снэпшот `.env`) | всегда `data/` + `.env` |
| Проверка | checksum + `PRAGMA integrity_check` на каждом | нет автоматической проверки |
| Ротация | да, настраиваемое число копий | нет, копится вручную |
| Восстановление | pre-restore снэпшот + авто-откат при ошибке | простое, без авто-отката |
| Доступ | ⚙️ бот → 💾 Бэкапы | `domain-monitor-server backup`/`restore <файл>` |

## Backup Manager 2.0 (через бота)

Меню 💾 Бэкапы показывает: включён ли автобэкап, интервал (часы), сколько
копий хранится, когда был последний, его размер.

### Два типа бэкапа

- **`db`** — только SQLite (основной файл + WAL + SHM). Быстрый, малый,
  покрывает 95% случаев (потеря/повреждение БД).
- **`full`** — то же самое плюс снэпшот переменных окружения (включая
  `BOT_TOKEN`/`ADMIN_API_KEY`) в архиве. Нужен для disaster recovery
  (полная потеря сервера) и как основа для ручной миграции
  (`migrate-export` использует тот же формат).

Выбор типа — в меню 💾 Бэкапы → 📦 Что сохранять, или при ручном запуске
кнопкой «Создать сейчас».

### Проверка целостности

Каждый созданный бэкап **сразу** проверяется: архив распаковывается во
временную папку, из него открывается отдельное sqlite-соединение и
выполняется `PRAGMA integrity_check`. Результат (checksum, verified)
сохраняется рядом с архивом (`.meta` файл) и виден в списке бэкапов.

**Непрошедший проверку бэкап никогда не участвует в ротации** — он
остаётся на диске для диагностики, но старые рабочие копии не
удаляются, пока не появится новый ПРОШЕДШИЙ проверку бэкап.

### Ротация

Настраиваемое число хранимых копий (💾 Бэкапы → ⏱ Расписание). Старые
копии удаляются только после того, как новая копия создана И прошла
проверку — никогда наоборот.

### Восстановление

Флоу из бота (💾 Бэкапы → список → выбрать файл → ♻️ Восстановить):

1. Выбор бэкапа из списка (видно: тип, размер, checksum, дата, verified).
2. Подтверждение — показывает, что именно заменится.
3. **Автоматический pre-restore снэпшот** текущего состояния (ещё до
   того, как что-либо тронуто) — сам становится обычной записью в
   списке бэкапов.
4. Проверка выбранного бэкапа (если вдруг он битый — восстановление
   прерывается, ничего не тронуто).
5. Замена файлов БД, `db.reopen()` (переоткрытие соединения без
   перезапуска процесса — все части приложения тут же видят
   восстановленные данные).
6. Применение миграций (на случай, если восстанавливается из более
   старой версии — additive-миграции применяются автоматически).
7. Healthcheck (`PRAGMA integrity_check` на восстановленных данных).
8. Результат сообщается явно.

**При любой ошибке на шагах 5-7 — автоматический откат** к pre-restore
снэпшоту из шага 3. Восстановление либо полностью удаётся, либо
оставляет всё как было (плюс сам pre-restore снэпшот остаётся в списке
бэкапов на случай ручного разбора).

### Concurrency

Нельзя одновременно: два бэкапа, бэкап и восстановление, два
восстановления (общий lock внутри `BackupTask`) — второй запрос просто
ждёт своей очереди, а не падает и не гонится с первым за один и тот же
файл. Отдельно: бэкап/восстановление **и активная миграция** — обе
стороны проверяют друг друга (создание бэкапа отказывает, если есть
активная задача `migrate-to`, и наоборот), потому что миграция
опирается на согласованный снимок тех же файлов БД. См.
[MIGRATION.md](MIGRATION.md#concurrency).

## CLI (`backup`/`restore`)

Не требует бота, работает даже если контейнер сервера остановлен.

```bash
domain-monitor-server backup              # создаёт ./backups/domain-monitor-server-backup-<timestamp>.tar.gz
domain-monitor-server restore <файл>      # запрашивает подтверждение, останавливает контейнер, восстанавливает, запускает заново
```

`restore` сам сохраняет текущие данные как `data.pre-restore.<timestamp>`
перед заменой (на хосте, не автоматический бэкап-объект, но так же не
теряет предыдущее состояние). Оба скрипта отказывают, если сейчас
выполняется миграция (`migrate-to`), по той же причине, что и
Backup Manager 2.0 — общая проверка через `/api/v1/migration/jobs/active`.

## Права доступа

И архивы бэкапов, и `.env`-файлы содержат секреты (`BOT_TOKEN`,
`ADMIN_API_KEY`). Всё, что их создаёт — Backup Manager 2.0, CLI
`backup`/`restore`, `migrate-export`/`migrate-to` — выставляет права
`0600` (только владелец) сразу при создании, не оставляя окна с более
широкими правами по умолчанию. `doctor` проверяет права на оба
расположения бэкапов (`data/backups/` и `./backups/`) и явно
предупреждает, если что-то доступно на чтение не только владельцу.
