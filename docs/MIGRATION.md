# Перенос центра управления на другой сервер

Два способа: автоматический (`migrate-to`, Migration 2.0) и ручной
(`migrate-export`/`migrate-import`, всегда работал и остаётся как fallback).
Автоматический покрывает почти все случаи; ручной нужен, когда до нового
сервера нет SSH-доступа с этого (например, установка идёт вручную кем-то
другим).

## Автоматический перенос (`migrate-to`)

### Требования

- Беспарольный SSH-доступ **с этого сервера** на новый (свой ключ этого
  сервера должен быть в `~/.ssh/authorized_keys` на новом — пароли
  никогда не запрашиваются и не принимаются).
- root на обоих серверах.
- Новый сервер — чистый Ubuntu/Debian (или уже с Docker/Compose/UFW —
  переустановлен не будет) с доступом в интернет.

### Шаги

```bash
domain-monitor-server migrate-to root@NEW_HOST
```

Что происходит:

1. **Диагностика этого сервера** (`doctor`) — если находит проблемы,
   спрашивает подтверждение продолжать.
2. Проверка SSH-доступа (root, беспарольно) и ОС на новом сервере.
3. Проверка, что уже стоит на новом сервере (Docker/Compose/UFW) —
   ничего не переустанавливается, если уже есть.
4. Сборка пакета миграции (та же база + фильтры + настройки + `.env`,
   что и в `migrate-export`) и проверка его целостности.
5. Копирование кода проекта и пакета на новый сервер (пакет — с правами
   `0600`).
6. Установка на новом сервере в **standby-режиме**: API и heartbeat
   живые (можно проверить `/healthz`), но Telegram-опрос выключен —
   поэтому два сервера никогда не будут одновременно опрашивать одного
   Telegram-бота.
7. Проверка `/healthz`, целостности БД и доступности Telegram API с
   нового сервера.
8. Регистрация задачи миграции (статус `standby`) — печатает номер
   задачи `<job_id>`.

На этом шаге **ничего необратимого не произошло**: агенты ничего не
знают о новом сервере, старый сервер продолжает работать как обычно.

### Опции

```bash
domain-monitor-server migrate-to root@NEW_HOST \
  -i /path/to/ssh/key \                          # если ключ не в стандартном месте
  --ssh-port 2222 \                               # если SSH на нестандартном порту
  --target-public-url https://monitor.example.com \  # см. «Стабильное имя» ниже
  --dry-run                                        # только проверки, ничего не переносить
```

`--dry-run` полностью безопасен для приватности: пакет миграции
собирается локально (чтобы проверить его целостность), но никогда не
копируется на новый сервер и удаляется сразу после проверки — реальные
данные никуда не уходят.

### Переключение агентов (`migrate-cutover`)

```bash
domain-monitor-server migrate-cutover <job_id>
```

Ничего не перезапускается. Это просто переводит задачу в статус
`cutover` — после этого heartbeat-эндпоинт старого сервера начинает
добавлять адрес нового сервера в ответ каждой ноде. Каждый агент **сам**
решает, переключаться ли:

1. не переключается сразу;
2. проверяет `/healthz` нового сервера;
3. шлёт туда authenticated heartbeat со своим текущим токеном;
4. только если новый сервер принял токен — сохраняет новый адрес
   (`/data/runtime.json` на агенте, не трогая host `.env`) и переключает
   uplink.

Старый агент, который не понимает это поле вообще, просто его игнорирует
и продолжает работать со старым сервером — ничего не ломается.

### Прогресс (`migrate-status`)

```bash
domain-monitor-server migrate-status <job_id>
```

Показывает по каждой ноде: ✅ переключилась / 🔄 ещё ждёт (видна на
старом сервере, но не на новом) / 🔴 офлайн (не видна нигде — как
правило, либо реально офлайн, либо слишком старый Agent, не умеющий
авто-переключение). То же самое видно и в боте:
⚙️ Настройки → 🚚 Миграция, там же кнопка **📋 Команды для оставшихся**,
которая печатает `domain-monitor-agent set-server <новый URL>` для
каждой не переключившейся ноды — ручной fallback, если авто-переключение
почему-то не сработало (офлайн-нода, старый Agent).

### Завершение (`migrate-finish`)

```bash
domain-monitor-server migrate-finish <job_id>
```

Когда все (или почти все — офлайн-ноды подхватят при следующем
подключении, задача продолжает предлагать им переключиться) ноды
переключились, этот шаг переключает сам Telegram-бот:

1. выключает Telegram-опрос на **старом** сервере (перезапуск, несколько
   секунд бот недоступен);
2. включает Telegram-опрос на **новом** сервере.

Порядок именно такой (старый выключается первым), чтобы никогда не было
окна с двумя одновременными опросами одного бот-токена — Telegram сам
разорвёт один из них с ошибкой 409, и не факт что тот, который нужно.

**Старый сервер и его данные не удаляются автоматически.** Когда
убедишься, что всё работает на новом — `domain-monitor-server stop` или
`uninstall` на старом, вручную и осознанно.

### Отмена (`migrate-cancel`)

```bash
domain-monitor-server migrate-cancel <job_id>
```

Останавливает предложение переключиться новым нодам. Ноды, которые уже
успели переключиться (после `migrate-cutover`), остаются на новом
сервере — отмена не двигает их обратно.

### Стабильное имя сервера

По умолчанию `PUBLIC_URL` на новом сервере — голый IP. Если завести DNS
A-запись на новый сервер заранее и передать её через
`--target-public-url`, при **следующей** миграции агентам вообще не
придётся ничего узнавать заново — достаточно поменять DNS-запись на
актуальный IP. Мастер установки (`install.sh`) тоже подсказывает это при
первой установке, если видит, что `PUBLIC_URL` — голый IP.

### Одновременность

Нельзя одновременно: два `migrate-to` (409 при попытке создать вторую
активную задачу), миграцию и бэкап/восстановление (обе стороны
проверяют друг друга — см. [BACKUP.md](BACKUP.md#concurrency)).

## Ручной перенос (`migrate-export`/`migrate-import`)

Более старый способ, всегда работал, остаётся как fallback — например,
если с этого сервера нет SSH-доступа к новому.

```bash
# На старом сервере:
domain-monitor-server migrate-export
# -> печатает путь к пакету, например ./backups/domain-monitor-migration-....tar.gz

# Скопировать файл на новый сервер (любым способом - scp, флешка, что угодно)
scp ./backups/domain-monitor-migration-....tar.gz root@NEW_HOST:/tmp/

# На новом сервере сначала установить Server:
curl -fsSL https://raw.githubusercontent.com/Theraf1u/domain-monitor/main/install.sh | sudo bash

# Затем:
domain-monitor-server migrate-import /tmp/domain-monitor-migration-....tar.gz
```

Токен бота, ID админов и admin-ключ переносятся из пакета; `PORT` и
`PUBLIC_URL` остаются собственными настройками нового сервера (умное
слияние `.env`, а не слепая перезапись). В конце печатается готовая
команда `domain-monitor-agent set-server <новый URL>` для каждой
существующей ноды — переключить их придётся вручную, авто-переключения
здесь нет (это разница с `migrate-to`).

**Важно**: перед тем как остановить старый сервер, убедись, что бот
на новом отвечает — иначе краткое время два процесса будут опрашивать
один Telegram-токен.

## Откат

Пока задача миграции не в статусе `completed` — старый сервер ничего не
теряет и не меняет своего поведения. `migrate-cancel` в любой момент
безопасен. После `migrate-finish` откат — это отдельная, новая миграция
в обратную сторону (со старого сервера, который всё ещё цел, на... уже
переключённый новый — или просто вручную стартовать `migrate-to` в
обратную сторону).
